This site is its own case study. It runs on a self-managed, hardened VPS, served by containers behind a TLS-terminating reverse proxy, and every git push ships it to production through a CI/CD pipeline — no manual steps, no SSH sessions to deploy.

Deployment Pipeline

Triggered on every push to main. The pipeline is defensive: it validates everything it can before touching production.

Prepare SSH

Step 1

Loads a dedicated deploy key and the server's pinned host key from encrypted secrets. Fails fast if the key isn't a usable private key.

Guard the target

Step 2

Verifies the destination really is the live project (compose file and certificates present). If not, the deploy aborts without changing anything.

Sync files

Step 3

rsync over SSH mirrors the repository to the server, explicitly excluding TLS material so certificates are never overwritten or exposed.

Rebuild & reload

Step 4

docker compose up --build bakes the new content into a fresh image, recreates the containers, reloads nginx and prunes old images.

Security Decisions

Key-only SSH

Password authentication disabled server-wide. A separate, revocable deploy key for CI keeps the personal key passphrase-protected.

Secrets out of the repo

Credentials live in encrypted CI secrets; TLS keys never leave the server — ignored by Git, the Docker build and the sync step.

Pinned host identity

The CI runner only trusts the server's known fingerprint, preventing man-in-the-middle attacks during deployment.

Minimal attack surface

Only the proxy is exposed; the app container is internal-only. HTTP is redirected to HTTPS and the image contains nothing but the site.

Postmortem

Resolved

~3-minute outage on the first automated deploy

Sep 2026 · Severity: low · Personal site
Impact
The proxy entered a restart loop and the site was unreachable for about three minutes.
Root cause
A stray character in the deploy-path secret made the pipeline sync to a new directory. Compose recreated the production containers from there, mounting an empty certificate folder, so nginx couldn't load TLS.
Resolution
Containers restarted from the correct directory, then the secret was fixed.
Prevention
Added a guard step that verifies the target is the live project before syncing anything, plus input sanitisation for all connection secrets. A bad path now fails the pipeline instead of the site.
